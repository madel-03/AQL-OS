# تذكيرات Telegram والموقع مغلق

الربط الحالي بالبوت يظل كما هو. التذكيرات اختيارية ومتوقفة افتراضيًا. لا يحتاج المستخدم إلى إبقاء الموقع أو جهازه مفتوحًا؛ الجدولة من Supabase ترسل طلبًا للخادم كل دقيقة.

## إعداد مرة واحدة

1. افتح `backend/migrations/telegram-reminders.sql` وانسخ محتواه إلى **Supabase → SQL Editor → Run**. شغّله كمالك المشروع بعد ملف `telegram.sql` السابق. يجهّز جداول السجل والجدولة وامتدادات Cron وpg_net وVault. `Success. No rows returned` طبيعي. الملف لا يفعّل الإرسال لأي مستخدم.
2. في PowerShell شغّل هذا السطر وحده لتوليد سر جديد ونسخه للحافظة:

   ```powershell
   node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('hex'))" | Set-Clipboard
   ```

3. أضف **Render → Environment → `TELEGRAM_REMINDER_SECRET`** والصق القيمة. هو سر مستقل؛ لا تغيّر `TELEGRAM_BOT_TOKEN` أو `TELEGRAM_WEBHOOK_SECRET` أو مفاتيح Google. لا ترسل السر في محادثة ولا تضعه في Git أو VITE.
4. انشر تحديثات backend إلى Render وfrontend إلى Vercel.
5. في عقل افتح **الخدمات → Telegram → تذكيرات، حتى والموقع مغلق**. فعّل التذكيرات، واختر مصادرها والتوقيت ثم **احفظ إعدادات التذكيرات**.

عند الحفظ لأول مرة، يضع الخادم عنوانه وسرّه في Supabase Vault ويثبّت وظيفة Cron باسم `aql-telegram-reminders` تعمل كل دقيقة. لا يُرسل السر إلى المتصفح، ولا تحتاج نسخه إلى SQL أو إلى خدمة خارجية. الوظيفة مشتركة، لكنها تفحص إعدادات كل حساب وربطه الخاص. لا تغيّر إعدادات المنطقة الزمنية تلقائيًا: تستخدم منطقة الربط المعروضة في الواجهة.

## تجربة التشغيل

1. اضغط **أرسل تذكيرًا تجريبيًا**: يرسل رسالة إلى حساب Telegram المرتبط بك فقط. قبولها يؤكد مسار الإرسال، ولا يثبت تشغيل Cron وحده.
2. خلال نحو دقيقة يجب أن تظهر قيمة حديثة لـ **آخر تشغيل للجدولة** و**آخر فحص لحسابك**. غياب الفحص الحديث يظهر تحذيرًا.
3. لتجربة الجدولة الفعلية: أنشئ موعدًا بعد نحو ٥ دقائق واختر التنبيه قبل ٥ دقائق، أو مهمة تستحق اليوم واختر وقت التذكير بعد دقائق. احفظ الإعدادات ثم أغلق الموقع وانتظر الرسالة في Telegram. لا تستخدم مهمة حساسة لاختبار دقة التوقيت.
4. سجل الإرسال يميّز «قبله Telegram» و«رُفض الإرسال» و«الإرسال غير مؤكد». القبول لا يعني القراءة على جهاز المستلم.

## ما الذي يُرسل؟

- عنوان الموعد مع تاريخ بدايته ووقته، عند البداية أو قبله بـ٥/١٠/١٥/٣٠/٦٠ دقيقة.
- عنوان المهمة غير المنجزة في يوم استحقاقها، عند وقت محلي تختاره. لا تذكيرات يومية متكررة للمهام المتأخرة من أيام سابقة.
- لا تُرسل مواعيد طوال اليوم أو مهام بلا تاريخ استحقاق. لا تغيير في بيانات التقويم أو المهام.
- إذا عاد الخادم بعد تأخير، يلحق تذكير الموعد حتى ١٠ دقائق بعد بدايته، وتذكير المهمة خلال بقية اليوم نفسه. المواعيد الأقدم لا تُرسل.
- قد تصل عدة تذكيرات في رسالة واحدة؛ حد ١٠ عناصر جديدة لكل حساب في دورة. التذكيرات التي عولجت سابقًا لا تمنع تقدم العناصر التالية.
- فحص الحسابات يتم على دفعات حتى ١٠ حسابات في الدورة، بأولوية الأقدم فحصًا وحد زمني للدورة. المهام بحد جلب ٥٠٠ مهمة مستحقة اليوم لكل حساب، والتقويم بحد ٥ صفحات. مشروع كبير يحتاج توسيع العامل/الطابور.

## الاستمرارية ومنع التكرار

البيانات والهوية محفوظة في Supabase، وليست ذاكرة العملية. قفل بمدة محدودة يمنع دورتين متزامنتين، وسجل occurrence فريد يمنع تكرار التنبيه بعد إعادة تشغيل الخادم أو إعادة طلب Cron. تغيير مهلة التنبيه لا يعيد إرسال الموعد نفسه؛ تغيير وقت بداية الموعد يصنع occurrence جديدًا. إعادة الربط بمحادثة مختلفة لا ترسل تلقائيًا قبل حفظ تفعيل جديد.

عند رفض صريح من Telegram يعاد نفس التنبيه حتى ثلاث محاولات، مع احترام `retry_after` وحد أدنى دقيقة، فقط إذا بقي ضمن نافذة التذكير. عند انقطاع الشبكة أو فقدان تأكيد الإرسال لا يُعاد الطلب تلقائيًا، لأن Telegram قد يكون استلمه. تعطل الخادم أثناء محاولة يتركها غير مؤكدة بعد انتهاء القفل، ولا يُرسلها مرتين. لا تدّعي هذه الآلية exactly-once أو ضمان التسليم. إذا حُظر البوت (403)، تتوقف تذكيرات الحساب حتى يرفع الحظر ويعيد التفعيل.

التعطيل والفصل يمنعان الطلبات التالية؛ رسالة قُبلت بالفعل لدى Telegram لا يمكن سحبها بهذه الميزة. يفحص العامل الإعدادات والربط مرة أخرى قبل الإرسال. تبقى التذكيرات المحلية في المتصفح مستقلة وقد ينتج عنها تنبيه إضافي داخل الموقع إن فعّلت المسارين.

## الاستضافة والتشخيص

الفحص كل دقيقة تقريبًا، وليس موعدًا مضمونًا بالثانية. استضافة Render المجانية قد تدخل السكون، والشبكة/الاستضافة/Supabase/Telegram قد تتأخر أو تتوقف. يلزم أن تكون خدمة الخادم وقاعدة البيانات متاحتين؛ هذه الميزة لا تضمن الاستمرارية أثناء توقف المشروع أو نفاد حدوده.

- خطأ الحفظ: شغّل SQL الجديد، وتأكد من وجود `TELEGRAM_REMINDER_SECRET` ثم أعد نشر الخادم.
- سر تغير بعد التشغيل: احفظ إعدادات التذكيرات مجددًا لتحديث نسخة Vault.
- «لا يوجد فحص حديث»: افتح Supabase → Cron وابحث عن `aql-telegram-reminders`. إن لم يوجد، احفظ تفعيل التذكيرات من الموقع. إن وجد لكنه لا يشغّل الخادم، تحقق من عنوان Render وإعداد السر والتوافر. سجل Cron يثبت تنفيذ SQL، أما heartbeat في عقل فيثبت وصول الطلب إلى العامل.
- 403 في نداء الجدولة: قد لا يتطابق سر Vault مع Render؛ أعد حفظ الإعدادات.
- خطأ امتداد في SQL: فعّل Supabase Cron وpg_net وVault من Dashboard ثم أعد تشغيل الملف. لا تواصل بعد خطأ الترحيل.
- تعذّر التقويم: يستمر تذكير المهام إذا أمكن تحميلها؛ غياب البيانات بسبب خطأ لا يُفسّر باعتباره عدم وجود مواعيد.

لتوقيف الجدولة المشتركة يدويًا كمالك قاعدة البيانات:

```sql
select cron.unschedule('aql-telegram-reminders');
```

إعادة حفظ تفعيل التذكيرات تثبّتها من جديد. سجلات التسليم تنظف بعد ٣٠ يومًا. الجداول والدوال الإدارية لا تُتاح لرموز مستخدمي المتصفح؛ الخادم وحده يستخدم service_role. لا تعرض محتويات Vault أو رؤوس HTTP في لقطات أو سجلات عامة.

## التحقق المحلي

`npm.cmd run test:telegram` من backend. اختبار الواجهة: `node scripts/verify-telegram-reminders-ui.js` مع frontend على 127.0.0.1:5175. الاختبارات تستخدم خدمات وقاعدة وهمية؛ الترحيل وCron الفعليان يُتحقق منهما عند تشغيل SQL وإعداد المشروع. لم نرسل رسائل إلى البوت الحقيقي أثناء التطوير.
