# AQL-OS

Life management application using React, Vite, Express, and Supabase.

## Structure

- `src/App.jsx`: screens, charts, and voice controls.
- `src/main.jsx`: React entry point.
- `src/index.css`: application styles.
- `src/lib/supabase.js`: browser Supabase client.
- `src/lib/lang.js`: language context and dictionary.
- `src/lib/i18n.jsx`: language provider.
- `../backend/server.js`: API, authentication, AI providers, and TTS.
- `../backend/agent-tools.js`: agent tool registry and execution.
- `../backend/test.js`: manual simulation script; currently needs a bearer token before use.

`dist/` is generated by the build. `node_modules/` contains installed dependencies.
Both are excluded from version control.

## Development

Run `npm install` separately in frontend and backend.
Keep configuration in each directory's `.env`; never commit secrets.

Frontend variables:
- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`
- `VITE_API_URL` (default: http://localhost:5000)

Backend variables:
- `SUPABASE_URL`
- `SUPABASE_SERVICE_KEY` (server only)
- `CEREBRAS_API_KEY`, `GROQ_API_KEY`, `GEMINI_API_KEY`
- `PORT` (default: 5000)

Run `npm start` in backend and `npm run dev` in frontend.
The project requires its Supabase tables and authentication configuration;
database migrations are not included.

## Checks

Frontend: `npm run build` and `npm run lint`.
Backend: `node --check server.js` and `node --check agent-tools.js`.
Existing lint errors remain to be addressed separately.
On Windows, use `npm.cmd` if PowerShell blocks `npm.ps1`.

## Research tasks

Open the **Workspace** home page (or the research area above chat). Enter a topic;
AQL plans search queries, searches the web, reads up to five different sites,
compares excerpts, checks citation IDs, and produces a UTF-8 Markdown download.
Completed reports can also be downloaded as a formatted PDF or editable Word
document. Both exports include clickable references, headings and tables, with
right-to-left formatting for Arabic. The Markdown option remains available.
It requires at least two readable sources and never treats failed page reads as
evidence. The report records source URLs, retrieval times, and limitations.

The authenticated API is `POST /api/research` with `{ topic, lang }`, followed
by `GET /api/research/:id` for progress and results. Each user can run one task
at a time. Refreshing or leaving the page does not stop a task while the backend
process remains running; the browser restores the most recent task for that user.

Tasks are saved in `backend/data/research/` when the backend starts from its own
directory. Set `AQL_DATA_DIR` to an absolute path on a persistent volume in
production. Ephemeral deployments can lose this data. This first implementation
requires a continuously running Node process: interrupted tasks must be restarted
after a server restart. It does not yet provide a distributed worker or scheduler.
Download reports before replacing local storage or redeploying without a volume.

Source pages are treated as untrusted evidence. Only public HTTPS HTML/text pages
are read; PDF parsing and pages requiring JavaScript or sign-in are not supported.
Automated citation checks validate reference IDs, not the factual truth of every
model-generated sentence. This is excerpt-based research, not an exhaustive review.

## Workspace and task library

The home screen now focuses on launching work, following current tasks, and
reopening saved reports. **Research** and **Create a report** launch the existing
research pipeline; **Plan a goal** transfers the goal into chat for discussion.
Planning does not pretend to execute a background task. Life balance metrics
remain available in an expandable section below the library.

`GET /api/research` returns up to 200 of the authenticated user's tasks, newest
first, without full report text. The shared research provider refreshes progress
across navigation. Opening a task fetches its details; completed tasks can be
previewed, downloaded as PDF/Word/Markdown, or carried into chat as a draft.
The library is backed by the existing task files and has the same persistent
volume requirement described above.

The AQL companion reflects real task and voice events: ready, thinking,
listening, speaking, completed, or needing attention. Completion notices appear
only for tasks seen progressing during the session, not for old reports loaded
from the library. Reduced-motion settings disable the decorative animations.

For isolated browser QA, start the frontend with
`npm run dev -- --host 127.0.0.1 --port 5175 --strictPort`, then run
`node scripts/verify-workspace-ui.js` from the backend. It intercepts API requests
in a separate headless browser, uses synthetic session/task data, and writes
screenshots to ignored `backend/data/workspace-qa/`. It does not create real
research tasks or change real user data.

## Appearance customization

Use **Appearance** in the page header to choose the glass surface inspired by the
reference video or the classic opaque panels. The controls include five built-in
backdrops, an optional personal photo, five accent colors, background dimming,
glass opacity and blur, corner radius, card density, animation and character
visibility. Changes apply immediately. The original generated room backdrop is
served locally from `public/backgrounds/warm-room.webp` (about 204 KB).

Preferences are saved locally under `aql-appearance-v1`. A custom JPG/PNG/WebP of
up to 8 MB is resized and saved as a WebP blob in IndexedDB; it is not uploaded to
the backend. These settings belong to the browser/device, not a cloud account,
and clearing browser storage removes them. **Remove photo** deletes the stored
photo, while **Reset the look** restores the default controls without deleting a
photo you may want to select again. System reduced-motion preferences are always
respected in addition to the animation switch.

Run `npm run test:appearance` in the frontend for saved-settings and input checks.
For full browser verification, use the workspace QA instructions above with
`node scripts/verify-workspace-ui.js --appearance`; this also checks persistence,
local photo upload/removal, controls, responsive settings and the existing task
flows. Screenshots are written to ignored `backend/data/appearance-qa/`.

Run `npm run test:research` in `backend/` to check the pipeline, citation rejection,
source restrictions, authentication, persistence, and isolation between users.

### PDF and Word export deployment

The backend uses `docx` for Word and Puppeteer/Chromium for PDF. Run `npm ci` in
the backend on deployment and allow Puppeteer's browser installation. The runtime
must have the Chrome system libraries installed and be able to launch headless
Chrome. If Chrome is provisioned separately, set `PUPPETEER_EXECUTABLE_PATH` to its
executable. Run as a non-root user with browser sandbox support.

The bundled open-source Noto Sans Arabic font lives in `backend/assets/fonts/`
with its OFL license, so PDF generation does not fetch fonts from the internet.
Keep this directory in the deployment. Word uses Arial and native RTL formatting.

`GET /api/research/:id/export?format=pdf` or `format=docx` requires the same user
authentication as the research task. Export failures leave the original report
available; they do not rerun research. At most two exports run concurrently per
backend process.

Run `node scripts/verify-report-export.js` from the backend to create Arabic and
English QA examples under ignored `data/export-qa/`. This launches headless
Chromium. PDF layout was visually checked on both languages. DOCX structure,
hyperlinks and RTL flags were checked; native Word/LibreOffice visual validation
requires an Office renderer installed on the machine.

## Living workspace tools

The home page includes six tool tabs and a suggestions box:

- **Focus:** a deadline-based timer with pause/resume, early finish, outcome notes,
  and saved session history. It continues to count elapsed running time across a
  page reload; a timer that expired while away opens the reflection screen when
  you return. This does not create operating-system notifications with the site
  closed. Sessions can be linked to projects; early finishes count only elapsed
  running time, and recording a session does not complete project steps.
- **My desk:** editable notes and pinned reports/projects. Reorder using the drag
  grip or the accessible earlier/later buttons. Report pins open the saved report.
- **Ideas:** a map of up to 24 recent research tasks, existing server goals, and
  local projects. Connections come from at least two shared title words or a
  user-created project link, not model-inferred semantic similarity. Select ideas
  to create a linked project or draft a planning conversation.
- **Projects:** editable checklists with a plant that grows from checked steps.
  A project without steps starts at zero, and deleting or unchecking steps updates
  its stage. Linked focus outcomes are visible on the project card.
- **Memory:** editable notes plus transparent activity facts. Forgetting an
  automatic fact hides it from future memory context; editing it replaces the
  generated wording. The first 12 visible entries accompany new chat requests.
  This does not erase old chat messages or source reports.
- **Atmosphere:** locally synthesized rain and café-like room textures, volume
  control, and optional lighting based on device time. Audio requires an explicit
  play action, never autoplays after reload, softens during AQL speech, mutes during
  microphone use, and stops when signing out. No recordings are fetched.
- **Suggestions:** at most two suggestions derived from failed tasks, repeated
  topics, unchanged projects or month-old reports. They never run automatically.
  Snooze for 24 hours, dismiss, or restore them from the box.

These new notes/projects/memories/sessions are stored under
`aql-studio-v1:<userId>` in browser localStorage, separate for each account.
They are **not cloud-synced** and clearing browser data removes them. Research
reports and server goals keep their existing server persistence. The local store
retains up to 75 notes, 60 pins, 30 projects with 30 steps each, 40 memory overrides,
and 100 focus sessions. Browser storage failures are surfaced in the tool panel.

The authenticated chat endpoint accepts `memory: string[]`; the backend limits
it to 12 non-empty entries of 280 characters each and labels it as user context,
not authority to change system rules or tool permissions.

```sh
npm run test:appearance
npm run build
# backend
npm run test:memory
npm run test:research
```

With the frontend running on `127.0.0.1:5175`, run

## Local device service (جهازي)

The workspace now includes a **My device / جهازي** tab. This is a separate local
bridge; the hosted backend never obtains filesystem access or the bridge key.
It supports browsing and reading text files, AI-generated project/file plans,
reviewing complete before/after content, approved writes and folder creation,
and JavaScript **syntax checks**. With local `--allow-run` opt-in it also supports
Node programs, npm dependency installation, and named project scripts. It does
not expose a general shell-command operation or a file-deletion operation.

On Windows, from `backend`, after installing its existing dependencies:

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\Desktop\AQL-Workspace"
npm.cmd run device -- --workspace "$env:USERPROFILE\Desktop\AQL-Workspace" --allow-run
```

Paste the printed key into **جهازي** and keep the terminal running. The bridge
listens only at `http://127.0.0.1:47831`; closing it revokes that session key.
The selected folder must already exist. Choose a separate working directory.
The key lives only in component memory, is cleared on disconnect/unmount, and
is never sent to the AI or stored in browser storage. Disconnecting the panel
clears its key but does not shut down the local process; use Ctrl+C for that.

Default allowed website origins are the current Vercel deployment, localhost
port 5173 and 127.0.0.1 ports 5173/5175. For another deployment, pass
`--origin https://your-exact-site.example`; this replaces the default allowlist.
Browsers may request local-network permission or block loopback access under
their security settings. The UI reports a connection failure; local-network
permissions must be enabled by the user. No tunneling or public listening port
is used. File browsing/editing is confined by the bridge's path checks, but
**executed programs run with the normal permissions of your OS account** and
can access other device files and the network. This is not an OS sandbox.

The authenticated hosted endpoint `POST /api/device/plan` only **plans**. It
receives the task, up to 100 currently visible filenames, and optionally the
selected file's first 45,000 characters after an explicit checkbox. The absolute
workspace path and device key remain local. No automatic recursive indexing or
background indexing occurs. The existing AI provider fallback is reused.

Every generated plan is revalidated by the local bridge. Preview IDs expire in
10 minutes and are single-use. Operations within a plan are serial and stop at
the first failure; earlier changes remain. File changes and syntax checks must
precede process steps. Changed
files are checked against the preview hash, and existing text is backed up in
`<workspace>/.aql-backups/` before replacement. Backups are JSON with `path` and
`content` for manual recovery. They stay on disk and may contain private text;
the bridge never exposes that hidden folder. Activity logs are in memory for
the current bridge session (up to 100 entries).

Paths must remain relative to the workspace. Dotfiles, dependency/build folders,
Windows device/ADS paths, symbolic links/junctions, hard-linked files and binary
files are rejected. Text files are limited to 180 KB; plans to 12 operations and
180 KB of generated content. `check_javascript` uses the Node executable with
`--check`, no shell, a timeout, bounded output and stripped Node option variables.
See [Node child-process documentation](https://nodejs.org/api/child_process.html).

### Diagnosing a failed task

Failed syntax/file operations and failed/timed-out local jobs show **Diagnose and
prepare a repair / حلّل الخطأ وجهّز إصلاحًا**. Clicking prepares local context only:
the last 12,000 log characters and the most relevant readable source (Node entry
file or npm package manifest). The user can edit the log, choose a different
source and explicitly tick file sharing before requesting an AI plan. Known
workspace paths/device keys and common credential patterns are redacted, but
this is not a guarantee that every secret is detected: review before sharing.

The backend bounds diagnostic fields, strips unrelated metadata and common
credential patterns, and treats logs as untrusted data. The model is instructed
to propose a minimal repair with verification, ask for unread source instead of
inventing its contents, and distinguish a server's time limit from a code defect.
Repairs use the same local preview, changed-file checks, backup and code-execution
approval as other plans. No automatic retries or background log uploads occur.
Success is reported by the actual verification job, not by the model's claim.

### Running projects

Restart an older bridge with `--allow-run`, then reconnect using the new key.
Without that flag, `run_node`, `npm_install`, and `npm_script` are rejected.
Plans containing these steps also require checking the explicit code-execution
consent box before the execute button becomes available. The bridge enforces
that approval too. Review shows the command, Node source or package manifest,
and the actual selected npm script content.

- Select a JS/MJS/CJS file to review running it directly with Node (no extra args).
- Select `package.json` to review dependency installation or enter a named script,
  such as `dev`, `build`, or `test`. These quick actions remain entirely local.
- Or ask the AI to build and run a project. Its process steps are enabled only
  when the connected bridge advertises the execution capability.

`npm install` uses `--ignore-scripts --no-audit --no-fund`, the public npm registry,
and disables npm workspaces. It installs versions listed in the project manifest,
never global packages. Direct file/URL/git dependency specs are rejected.
Project `.npmrc` and `npm-shrinkwrap.json` require manual review/removal before
bridge npm execution. User/global npm config are replaced by temporary empty
configs and backend secret/Node-option environment variables are not inherited.
Some packages requiring install-time build scripts may need manual setup.
`npm run <name> --ignore-scripts` executes the selected script while skipping
its automatic pre/post hooks; the selected script itself can run shell commands
and other programs. See [npm's script behavior](https://docs.npmjs.com/cli/v11/commands/npm-run/)
and [ignore-scripts](https://docs.npmjs.com/cli/v11/commands/npm-install/#ignore-scripts).

Process work returns a job ID immediately and is monitored through authenticated
`GET /jobs`; `POST /stop` stops that job. Output stays local, bounded to the latest
100,000 characters per job, with up to 30 retained jobs and at most two concurrent
jobs. The default total job deadline is 15 minutes. Nonzero exits, stopping,
timeouts and skipped downstream steps are reported separately. Input file hashes
are checked again before launch. The UI links loopback HTTP addresses printed by
running servers. It never embeds untrusted process output as HTML.

Leaving the tab, disconnecting, or reloading does **not** stop jobs. Reconnect with
the same bridge key to regain controls. Ctrl+C/SIGTERM asks the bridge to stop
its jobs. On Windows it uses `taskkill /PID <pid> /T /F`; on POSIX it kills the
spawned process group. This is process-tree cleanup, not containment of hostile
code that deliberately escapes its tree. **Only direct bridge file replacements
are backed up**; package installs and runtime side effects are not backed up or
rolled back.

Verification:

```powershell
# backend
npm.cmd run test:device
node scripts/verify-device-ui.js
# Optional: calls the configured Groq account with a synthetic cafe-page request
node scripts/verify-device-live.js
node scripts/verify-device-live.js --run
# Optional: actual public-registry package download and project-script execution
node scripts/verify-device-packages.js
```

UI QA requires frontend at 127.0.0.1:5175 and bridge port 47831 to be free. It uses
isolated fake auth and AI responses, a **real** local bridge and real QA files.
UI QA also starts a real npm server, checks its HTTP response, stops it and
verifies its child-server port closed. Unit tests cover execution opt-in and
consent, timeouts, cancellation, bounded logs, stale sources, install/pre/post-hook
suppression and secret-free environments. The live smoke test separately checks
real AI generation through local execution and optional HTTP server startup.
Screenshots and sample projects remain under ignored `backend/data/device-qa/`.


## Google Calendar

The **My calendar / تقويمي** tab connects the primary Google calendar, lists the
next 14 days (with pagination), and creates timed events after explicit review.
Times use the browser's timezone and are sent as ISO instants. Google all-day end
dates are exclusive and rendered accordingly. Stable event IDs prevent duplicate
inserts when retrying the same save after a lost response. No guests, invitations,
event editing/deletion, Google Tasks, or automatic AI calendar access are included.

Follow [the Arabic setup guide](../backend/CALENDAR-SETUP.md). Run
`backend/migrations/calendar.sql` in Supabase, configure GOOGLE_CLIENT_ID,
GOOGLE_CLIENT_SECRET, GOOGLE_REDIRECT_URI, APP_URL and CALENDAR_TOKEN_KEY on the
backend, then deploy both sides. The interface shows setup-required status until
credentials are configured. Tokens are encrypted in Supabase with AES-256-GCM,
not returned to browsers. OAuth uses single-use server state and an HttpOnly
browser-binding cookie established by top-level navigation. Scopes are restricted
to owned-calendar events. Disconnect revokes Google access before local deletion.

Backend checks: `npm.cmd run test:calendar`. UI checks (frontend on 5175):
`node scripts/verify-calendar-ui.js`. These use mock Google responses; real account
authorization must be tested after setup. Keep the encryption key stable across
deployments; losing it requires reconnecting accounts.


## Personal tasks (مهامي)

Run `backend/migrations/tasks.sql` once in the Supabase SQL editor, then deploy
backend and frontend updates. No additional Google scopes or OAuth client setup
are needed. `/api/tasks` is authenticated and every query filters by the session
user. Browser access to the table is revoked; writes use the backend service role.
Tasks are separate from Google Tasks, home chores, goals, and local project steps.

The Tasks tab adds/edits titles, notes and optional calendar-date deadlines, marks
tasks complete or reopens them, and filters pending/completed/overdue/all. Dates
are local calendar dates (no UTC midnight conversion). The latest 500 tasks are
loaded. Stable creation IDs prevent duplicate records when the same POST is retried.

“Make time in Google Calendar” opens the existing calendar review flow with the
task title/notes and a suggested one-hour slot on its due date, when present.
Review the time before saving. A stable event ID based on the task ID prevents
duplicate scheduling of the same task. The event is independent: changing or
completing the task does not edit/delete the Google event. Schedule changes to an
already-created task event must be made in Google Calendar. There are no automatic
reminders, background notifications or Google Tasks synchronization in this version.

## Voice wake mode (يا جارفس)

The header microphone control opens a session-only voice panel. Enable it with
a click and allow the microphone, then say **يا جارفس، وش عندي اليوم؟**. Jarvis
Arabic spellings and English Jarvis are accepted. The name is editable and saved
per account in browser storage; the microphone enable state is never persisted.
You may also say just the name, wait for the spoken acknowledgement, then ask
one question within ten seconds. After that request, the wake name is required
again. Ambient/interim results do not become chat requests.

Today's summary refreshes account tasks and the primary calendar directly,
including overdue pending tasks, and reports unavailable/disconnected sources
explicitly. Calendar/task data is not sent to AI chat for this summary. Other
questions use the existing authenticated chat with read-only voice instructions
and existing account memory; those questions/replies are saved by the existing
chat route. Change/run/send requests are not executed by voice. Navigation such
as “افتح المهام” and “افتح التقويم” opens the relevant existing tool.

Speech recognition is the browser Web Speech API, **not an offline/local wake-word
model**. The browser recognition service may transmit microphone audio even
before the wake name. AQL itself sends only the post-wake question to its chat
endpoint. Response text uses the existing backend TTS service, including day
summary text; browser speech synthesis is its existing fallback. These limits
are disclosed before activation. See [MDN SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition).

Recognition is detached/aborted during processing and spoken replies to avoid
self-triggering. Existing app microphones claim priority. Recognition resumes
after their idle event, and enabling during existing speech waits for that
speech to finish. Network/service/permission errors stop recognition and require
a manual retry; no uncontrolled error retry loop is used. Normal service end
events reconnect with a delay while enabled.

Hiding/closing the page stops the wake session and pending voice request; returning
to the page requires re-enabling. Stop is available both in the panel and next to
the active microphone control. Closing the settings dialog alone keeps the
visible-page session enabled. No closed-page, lock-screen or background listening
is implemented, and no desktop app has been added. Support/availability and real
Arabic recognition accuracy depend on browser, microphone and recognition service.

Checks: frontend `npm.cmd run test:wake` and backend
`node scripts/verify-wake-ui.js` with frontend on port 5175. The browser test
simulates recognition and playback, verifies today versus chat privacy, command
follow-up, custom names, no auto-start/self-echo, permission/visibility cleanup,
other microphone arbitration and mobile layout. It **does not validate real
microphone recognition or acoustic accuracy**. Existing real TTS tests cover voice
synthesis separately. QA screenshots are under ignored `backend/data/wake-qa/`.
Deploy frontend and backend updates; no migration or new API key is needed.


### Home voice presence

The home hero now renders the wake assistant as a CSS light creature with
orbits and a waveform, direct enable/stop controls, a settings shortcut, and
the last request/reply. Movement reflects session state (idle, waiting, command,
processing, speaking, hidden/error); it is **not** a microphone amplitude or
frequency measurement. It honors both OS reduced-motion and the app motion
preference. Hiding the decorative companion hides the creature but retains
voice controls. The full privacy explanation is available in settings; a short
online-recognition disclosure remains next to the home controls before enabling.

The visual is portaled into the home hero from the single persistent wake
controller. Changing pages or returning home does not create a second recognition
session. The header settings/stop controls remain available on other pages.
`verify-wake-ui.js` also checks home activation, visual states, reduced motion,
mobile layout and navigation without an extra microphone session. Screenshots
include `backend/data/wake-qa/home-presence-ar.png`. No new runtime dependencies
or backend changes are needed for this presentation update.
